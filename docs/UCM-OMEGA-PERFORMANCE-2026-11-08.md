# UCM-Ω：保留因果审查的推演性能优化（2026-11-08）

## 性能瓶颈

目前正式生成的是 **1 条世界线、6 个先后依赖的历史时段**。未触发额外请求时共 8 次 DeepSeek 调用：干预解释 1 次、按年推进 6 次、总结 1 次。以下优化不改变数量、不减少事件配额或因果校验。额外的全球覆盖补充、因果修复和窗口细分仍按需执行。

在没有真实账户调用明细和时延测试的情况下，不能宣称网站已达到某一个百分比的实际加速，也不能保证不同采样时得到逐字相同的推演。

## 已实施

1. **让 DeepSeek 自动上下文缓存更容易命中**：此前相同规则前夹有动态年份、情景和事件数据，每个时段的提示词首段不同。现在把所有原有共同推演规则作为稳定的长前缀，后接当前时段事实、干预、可用因果引用和 JSON 输出格式。原有内容未删减，年份与世界状态仍逐窗口传递。根据 DeepSeek 官方缓存文档，缓存自动开启，稳定前缀有助于缓存命中；**缓存是否命中、加速多少由 DeepSeek 决定**。
2. **避免已确认超限的重复完整推演**：DeepSeek 历史窗口输出明确返回 `finish_reason: length`，且已经使用 8,192 Token 输出上限时，不再拿同样的上限重新完整生成一次；直接交由已有 `runAdaptiveWindow` 沿时间拆分，并在必要时继续按地区/领域拆分。审查、全年覆盖、完整事件保留和全局因果复核不变。空 JSON、非 JSON、其他模型/阶段继续执行原有恢复机制。
3. **逐请求真实耗时统计**：对成功/失败/JSON 重试单独记录请求开始至响应 JSON 完成的耗时（毫秒）、模型及无敏感信息的阶段标签。分为历史干预识别、历史时段推演、全球覆盖审查、因果修复、总结和总结格式恢复。
4. **设置中的诊断仪表盘**：展示已测 API 请求的平均耗时，并在“推演各阶段的真实等待时间”里呈现最近 300 次记录的调用次数、平均耗时、累计请求时间和失败次数。旧记录没有开始时间，不会伪造；这些时间相加不一定等于整场推演的墙钟时间。
5. **隐私约束**：仍然只在本机 `localStorage` 保存用量摘要；不持久化 API Key、原始历史输入、完整提示词或模型输出。

## 未采取的方案

- **没有**开启多代理共同编写同一时段，也没有重复生成两套完整历史再择优。
- **没有**缩短历史的输出内容、关闭世界覆盖审查、删去因果修复或削减推演年代。
- **没有**仅仅加快页面进度条或冒充服务端加速。

## 验证

`tests/cached-prompt-performance.test.mjs` 与既有测试共同验证：6 个连续历史时段共享足够长的模型输入前缀、所有主要推演规则与因果 ID 不丢失、每次请求耗时按阶段正确记录、用户密钥不进账本、已确认输出超限能够跳过无效完整重试并继续细分，同时保证单条世界线及原有全球因果检查不变。
