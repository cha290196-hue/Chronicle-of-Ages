# UCM-Ω — 双情景并行加速（2026-11-08）

## 优化前的主要瓶颈

默认两套候选历史情景 × 六个时间窗口，每套的后续年份依赖前期结果。先前代码按情景 A 的六个窗口、情景 B 的六个窗口**全部串行**执行，连彼此完全独立的 A 和 B 都要排队等待。模型输出过长时，还可能产生格式恢复、历史窗口细分、区域审查等额外请求。

## 当前优化

### 因果依赖驱动的多代理执行

- 每个候选情景是独立的因果推演任务，彼此共享用户干预和世界线分叉之前的现实/父分支历史，但**绝不共享各自分叉后的临时事件、事实或未经审核的输出**。
- 默认使用 **2 个并行工作任务**，与默认 **2 套候选情景**一一对应。内部支持显式设置 `maxParallelScenarios`，硬上限 3，避免不受控的并发和服务商限流。
- 每个情景仍按其六个时间窗口逐次推演。单窗口 JSON 格式恢复、因果修复、全球覆盖补充、自动细分和审计全部保留。
- 每条候选历史完成后，照常进行全局因果复核；两条均完成并通过检查后，保持既有评分排序方法，在最终汇总模型调用中选择最佳方案。
- 任何一个情景发生致命异常，统一调度器都会中止其余情景的正在进行的请求，并等待其终止，不把部分结果保存成完整世界线。原有“停止推演”按钮会中止所有并行任务。
- 进度条显示**已完成历史窗口 / 总计划窗口**，同时标注当前并行情景数；动态追加的历史细分任务仍计入总量。

### 不以降低推演规格换速度

未减少候选情景数（2）、历史窗口数（每情景 6）、单次输出上限、事件保留数量、因果/年代审核、全局核验、全球覆盖补充或模型使用参数（包括 Thinking 模式设置）。这是**任务调度层**优化，不是降低模型推理标准。

### 性能与边界

对两个独立情景，原本的历史计算延迟近似等于 A、B 的耗时之和；现在主要取决于它们中耗时更长的一个，另加共同输入解析和最终汇总的串行时间。用同样的模拟 API 延迟、历史事件和审计数据进行串行/并行对比的回归测试会报告真实测得的耗时。

实际获得的加速取决于 DeepSeek 的请求排队、吞吐量、模型延迟、API 并发配额、是否触发错误恢复，以及两套情景耗时差异。无法保证任何随机大模型在不同时序执行时逐字生成相同历史叙述，更无法保证历史推断永远正确，但这次**没有缩减任何原有推演步骤或信息预算**。

### 质量保障

- `tests/parallel-ensembles.test.mjs`：验证两个情景确实同时启动，时间窗口保持严格先后顺序；单线程和多线程调度得到相同的审查结果与排名；并发上限可靠；错误或用户中止时，所有未完成请求均被取消；真实模拟器适配器将取消信号传入模型调用。
- `tests/parallel-performance.test.mjs`：在相同模拟模型时延、事件数量和因果约束下，测量串行和并行两种策略的实际墙钟时间并验证并行更快。
