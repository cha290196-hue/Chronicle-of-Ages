# UCM-Ω 纠偏：只生成一条完整历史，而非整条历史重复算两遍

**日期：2026-11-08。**

## 发现与决策

此前正式推演使用 `scenarioCount: 2, maxWindows: 6`，完整计算两条独立候选历史，然后按 `evaluateScenario` 的启发式分数选择其中一条。后续把这两条候选并行，仅减少了墙钟等待，并**没有减少模型需要生成的完整历史数量或相应 Token**。

这并不属于“多个子代理协作生成一条历史”。候选选择得分主要反映因果引用完整性、事件/领域覆盖等结构特点，**不是历史真实性、合理性或可靠性的校准概率**。无论是串行还是并行，不能把这种“择优”说成确保推演质量。

本次改动直接恢复到单条因果主链：

1. 生产入口 `simulate()` 传入 `scenarioCount:1`，`simulateOmega` 和 `runMatrix` 默认亦为 1。
2. 撤掉多情景并行调度及相关界面提示、性能宣传和已不再适用的并发测试。
3. 保留六个历史时段按时间依赖顺序演化，不跳过年份、不以减少事件输出量换速度。
4. 保留每次候选事件的因果校验、无效引用修复、全球历史覆盖补充、结构化输出截断后按时间/地区/领域的细分和完整时间线因果复核。
5. 不假称所谓多个子代理在协作。真实单次基础请求量由 **14 次降为 8 次**（1 次解释干预 + 6 次历史推演 + 1 次完整汇总），只要无需额外审核、修复或细分。Token 消耗不等于次数，实际费用按仪表盘报告。真实延迟仍取决于 DeepSeek 与历史复杂度。

## 不是没有代价

双候选生成本来可能提供一定的思路多样性或不确定性比较。取消完整的第二候选可降低重复开销，但**无法数学保证与双候选择优得到相同的历史推断质量**。以前的选择指标也没有经过证明能提高历史正确性。因此这是明确放弃未经验证的候选策略，而非宣称质量绝对不变。

## 为什么暂不把世界线拆给多个代理合写

同一阶段的国家、经济、科技、气候和战争具有耦合关系。没有冻结的共享世界状态、事件引用协议、跨部门冲突仲裁及前后阶段的统一提交门槛时，直接让若干子代理并行编写不同地区会出现彼此不知对方历史前提、因果链断裂或矛盾的风险。

未来如果要安全增加协作式代理，应当先完成并测试：

- **单一权威世界状态**：所有代理读取同一个已审核历史快照，只能提交候选变动，不能各自重写世界线；
- **任务依赖有向图**：有实质依赖的任务必须串行；经核定独立的阅读、检索、反例寻找才可并行；
- **统一因果提交**：全局检查时间、跨地区贸易/冲突、技术先决条件和互斥资源条件，再原子化更新主状态；
- **评估基准**：相同干预下对比真实性校验、事实覆盖、矛盾率、调用时延、请求次数和总 Token；只有实证同时满足约束才能默认打开协作。

在这些前置条件未满足之前，**不引入多代理并行历史编写**。因此本次纠偏没有做“复杂问题全员并行”之类冒险优化。

## 验证

`tests/single-canonical-history.test.mjs` 会以替身 Chat API 检查：单条正式推演、6 个时序历史窗口、无第二候选、8 次基本模型调用、原有事件账本和因果审核正常、生产入口明确禁用双候选。原有世界线、历史覆盖、知识系统与 JSON 错误恢复测试均继续运行。
